# metamui-sr25519

sr25519 — Schnorr signatures over Ristretto255 with Merlin transcripts, the
`schnorrkel` scheme used by Substrate and Polkadot — in portable scalar Rust,
verified against `w3f/schnorrkel` 0.11.4 in both directions. The
`metamui-sr25519-wasm` wrapper in this distribution is a thin binding over
this crate; the crate can also be used directly.

## What is implemented

| operation | rule |
|---|---|
| key generation | a 32-byte mini-secret is the secret key. It expands as `MiniSecretKey::expand(ExpansionMode::Ed25519)`: `SHA-512(mini)` → clamped scalar (divided by the cofactor 8) ‖ 32-byte nonce seed; `A = [a]B` on the Ristretto basepoint, encoded per RFC 9496 |
| signing | schnorrkel `sign_simple`: Merlin transcript `SigningContext(ctx) ‖ sign-bytes(M) ‖ proto-name "Schnorr-sig" ‖ sign:pk ‖ sign:R`, challenge `c` by wide (64-byte) reduction, `s = r + c·a`. The witness `r` is derived from the nonce seed and the transcript with no operating-system randomness, so signing is **deterministic**; schnorrkel's own signer mixes in an RNG, and its verifier accepts both |
| verification | schnorrkel `verify_simple`: `[s]B = R + [c]A`. Rejects a signature without the schnorrkel flag bit (`sig[63] & 0x80`), a non-canonical `s`, and an `R` or `A` that is not a valid Ristretto255 encoding (which implies prime-order subgroup membership) |
| derivation | Substrate-style paths: `//name` or `//0` is a **hard** junction (chain code = SCALE-encoded junction, schnorrkel `HDKD-hard` transcript); `/name` is a **soft** junction, which is **not implemented** and returns `KeyDerivationError` rather than a placeholder key. Hard derivation is not gated against a Substrate vector and does **not** currently reproduce `sp_core`'s keys (the dev phrase's `//Alice` differs); treat it as this crate's own scheme until a vector gate exists |

### Signing context

Every `sign` / `verify` without an explicit context uses the schnorrkel
context `b"substrate"` (`signing_context(b"substrate")`), which is what
Substrate wallets and runtimes use. An explicit **empty** context is a
different signing domain: a signature made under `b""` does not verify under
`b"substrate"` and vice versa. The `*_with_context` entry points take the
context as bytes.

## Sizes

| item | bytes |
|---|---|
| mini-secret (seed) | 32 |
| public key | 32 (Ristretto255 canonical encoding) |
| signature | 64 = `R` ‖ `s`, `s[31]` carrying the schnorrkel flag bit |

## Usage

```rust
use metamui_sr25519::Sr25519Signer;

let signer = Sr25519Signer::generate();             // seed from the operating system
let pk = signer.public_key();                       // Vec<u8>, 32 bytes

let sig = signer.sign(b"hello")?;                   // context b"substrate"
assert!(signer.verify(&sig, b"hello", &pk)?);

let sig = signer.sign_with_context(b"hello", b"my-protocol")?;
assert!(signer.verify_with_context(&sig, b"hello", &pk, b"my-protocol")?);

// A seed is an ordinary secret key; a hard path derives a child.
let alice = Sr25519Signer::from_seed(&[0x24u8; 32])?.derive_from_path("//Alice")?;
# Ok::<(), metamui_sr25519::Sr25519Error>(())
```

`Sr25519Signer` holds only the mini-secret and zeroizes it on drop. The
free functions (`generate_keypair`, `keypair_from_seed`, `sign`, `verify`,
`sign_with_context`, `verify_with_context`, `derive_keypair_from_path`,
`derive_public_from_path`, `is_valid_public_key`, `is_valid_signature`, and
their `_hex` forms) are the same operations on `Vec<u8>` and `0x`-hex
strings, for bindings. `sr25519::Sr25519` is the byte-level core
(`expand_mini_secret_key`, `get_public_key`, `sign`, `verify`), and `merlin`,
`strobe` and `native::ristretto` are the transcript, STROBE-128 and
Ristretto255 layers beneath it; they are public so the tests can reach them.
`derive_from_mnemonic` is not implemented and returns `MnemonicError`.

## Features

| feature | default | what it does |
|---|---|---|
| `std` | yes | without it the crate is `#![no_std]` + `alloc`. Only this crate's own code is checked that way; the dependency closure is not built for a no-std target |

Every code path is portable scalar Rust; there is no SIMD, assembly or GPU
path and no CPU-feature detection. Hashing is the in-tree `metamui-sha2`,
`metamui-sha3` (Keccak-f for STROBE) and `metamui-blake2b`; no external
crypto crate is in the dependency closure. `schnorrkel` and `merlin` appear
only as dev-dependencies, as test oracles.

## Tests

```
cargo test -p metamui-sr25519 --release
```

* `tests/kat_schnorrkel.rs` — `test-vectors/sr25519/sr25519-schnorrkel-kat.json`
  (generated by `schnorrkel` 0.11.4 through `examples/gen_schnorrkel_kat.rs`)
  on three axes: (A) public-key derivation equals schnorrkel's, (B) this
  verifier accepts schnorrkel's signatures, (C) schnorrkel accepts this
  crate's signatures; plus an internal round trip. A missing file fails the
  run, nothing skips.
* `tests/merlin_parity_kat.rs` — `MerlinTranscript` against the reference
  `merlin` 3.0.0 crate, byte for byte, across label and message lengths that
  cross the STROBE rate.
* `tests/ristretto_kat.rs` — RFC 9496 Appendix A: the encodings of
  `0·B … 15·B` and the invalid-encoding set.
* Unit tests in `src/` cover expansion, hard derivation (`//Alice`) and the
  soft-derivation refusal.

Of the other files in `test-vectors/sr25519/`, `merlin_transcript_traces.json`
is read by the Swift binding's Merlin gate (the Rust gate uses the `merlin`
crate directly), and `sr25519-schnorrkel-vectors.json` is a legacy corpus
that no gate replays.

## What is and is not claimed

Secret-dependent selection and comparison in the field, scalar and curve
code use `subtle` idioms, and the mini-secret is zeroized on drop. **No
timing or side-channel measurement has been made and no independent audit
has taken place**; treat the implementation as designed for constant time
and unmeasured. Fault and power attacks are out of scope. See `SECURITY.md`
at the root of the distribution for what a security report should contain.

Signatures produced by releases before the 2026 schnorrkel-compliance
rework used a different transcript layout and do not verify under this
code; re-sign such data. No compatibility shim is provided.

### Package name

Until 1.0.0-rc.4 this package was published as `metamui-crypto-sr25519`
(library `metamui_crypto_sr25519`). The code is the same portable scalar
implementation; a consumer pinning the old name must update the dependency
name and the `use` path:

```toml
metamui-sr25519 = "1.0.0-rc.5"
```
