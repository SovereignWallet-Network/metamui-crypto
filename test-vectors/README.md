# Test Vectors

Canonical test vector directory for MetaMUI Crypto Primitives.
One flat directory per algorithm — no subdirectories within algorithm dirs.

## Which directories are conformance evidence

Two kinds of file live here and they prove different things:

* **`*-upstream/`** (and `smaug-t/v1.2.0-kat/`) hold vectors produced by an
  independent reference — NIST ACVP, an official submission package, or a
  build of the upstream C reference. Reproducing them byte-for-byte is a
  conformance proof. Each has a `SHA256SUMS` and a per-binding gate; a gate
  refuses to run against a file carrying a self-generated marker.
* **Everything else** is interop or convenience data: generated by this repo's
  own implementations to check that ten bindings agree with each other.
  Agreement is worth testing and is *not* evidence of conformance — if the
  canonical implementation is wrong, every binding reproduces the same wrong
  bytes. Do not cite these directories as a standards claim.

The fourteen genuine-oracle directories are: `aimer-upstream/`,
`classic-mceliece-upstream/`, `falcon-upstream/`, `frodokem-upstream/`,
`haetae-upstream/`, `hqc-upstream/`, `lms-upstream/`, `ml-dsa-upstream/`,
`ml-kem-upstream/`, `ntru-plus-upstream/`, `ntru-prime-upstream/`,
`slh-dsa-upstream/`, `xmss-upstream/` and `smaug-t/v1.2.0-kat/`.

## Notes

- **Keccak-256 vs SHA3-256**: `keccak256/` contains the Ethereum pre-NIST variant (padding 0x01).
  NIST SHA3-256 (padding 0x06) vectors are in `sha-3/`.
- **sr25519**: Non-deterministic algorithm — comprehensive KAT sets are not feasible.
  The single vector verifies a known-good signature from the w3f/schnorrkel reference test suite.
- **Deoxys**: 5 KAT vectors from the oasisprotocol/deoxysii-rust reference implementation are
  in `deoxys/deoxys-oasisprotocol-vectors.json`. The original SUPERCOP/CAESAR KAT files are
  also available in the SUPERCOP benchmark repository.
- **Ed25519-ZIP-215**: `ed25519/zip215-vectors.json` covers ZIP-215 edge cases not present in
  RFC 8032: small-order public keys, non-canonical encodings, and the cofactored verification
  equation. Each of the 6 vectors carries three independent acceptance columns, documented in
  the file's own `verification_profiles` block:
  - `valid_zip215` — ZIP-215 §2 cofactored rules (5 of 6 accepted).
  - `valid_strict` — historical: this repo's strict profile until 2026-09-24, cofactorless
    verification plus canonical-encoding and small-order-public-key screens (1 of 6 accepted),
    matching libsodium and ed25519-dalek's `verify_strict`. No target implements it now.
  - `valid_rfc8032_cofactorless` — a bare RFC 8032 §5.1.7 verifier with no added policy, e.g.
    Go's `crypto/ed25519` (2 of 6 accepted).

  The strict and bare-RFC-8032 columns differ on exactly one vector, `tc_2` (identity public key,
  s = 0), which a bare verifier accepts because the equation reduces to `O = O + [k]O`. The
  column was renamed from `valid_rfc8032` for that reason: the old name asserted a spec mandate
  that does not exist.
- **Ed25519 verification policy**: `ed25519/ed25519-policy-vectors.json` is the oracle for the
  policy every target implements since 2026-09-24, **RFC 8032 as written** — §5.1.3 decoding of
  A and R (y ≥ p, x = 0 with the sign bit and no square root all fail), S < L, the cofactored
  equation, no small-order screen — and for ZIP-215 where a target has it. 37 cases: honest
  signatures and RFC 8032 §7.1 tests, tampering, S range, non-canonical R and A, mixed-order R
  and A, all eight small-order keys, off-curve points. `tools/ed25519-policy-gen/gen.py` computes
  both verdicts from the text; `zebra-check` recomputes them with ed25519-zebra and
  curve25519-dalek; `genrun.sh` vendors only when they agree. Every target's policy gate replays
  it (`documents/public-release/api-contract.md` §12.1).
