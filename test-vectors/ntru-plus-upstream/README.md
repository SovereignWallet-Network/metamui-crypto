# NTRU+ — genuine upstream KAT (conformance gate)

The NTRU+ authors' own published Known-Answer-Test records for the three
parameter sets of the 2026 revision (ntruplus768 / 864 / 1152), copied
verbatim from the reference implementation's `KAT/` directory:

    https://github.com/ntruplus/ntruplus — commit 621c667 (2026-03-19),
    specification dated 2026-02-02, vendored as the git submodule
    metamui-crypto-reference/c/ntruplus-ref

`ntru-plus-upstream.json` records the SHA-256 of each source `.rsp` file.

## Why this replaces the previous oracle

The previous oracle in this directory was generated by MetaMUI from the 2025
KpqClean v2.0.0 reference with a SHA-512-counter `randombytes` of our own
design. It was genuine for that revision, but the 2026 reference is a
different algorithm on the wire:

| changed in the 2026 revision | effect |
|---|---|
| `poly_tobytes` / `poly_frombytes`: sequential 2-coefficients-per-3-bytes packing (was interleaved 64-coefficient blocks) | every pk / sk / ct byte |
| `poly_cbd1` and SOTP: byte `i` paired with byte `i + N/8` (was 16-bit little-endian words with an interleaved index) | every sampled polynomial |
| `hash_f`: SHAKE-256 (was SHA-256) | sk tail, ct, ss |
| Montgomery convention: `basemul` returns plain-domain values (× R²), `fqinv` × R⁻¹, `invntt` scaling constants `NINV`/`2NINV` | every NTT-domain byte |
| keygen: h⁻¹ = f · g⁻¹ (was `baseinv(h)`) | none (same value) |
| parameter sets: 768 / 864 / 1152 only | 576 dropped |

No byte of pk/sk/ct/ss is comparable across the two revisions, so the old
vectors could not be "migrated"; they were replaced by the authors' files.

## Randomness model

The records come from the NIST `PQCgenKAT_kem` harness: `randombytes` is the
AES-256-CTR-DRBG **without** derivation function, seeded once per record with
the 48-byte `seed` (`randombytes_init(seed, NULL, 256)`). Keygen draws
`randombytes(32)` per sampling attempt — f first, then g, each retried until
invertible — and encaps draws `randombytes(N/8)` for the message. A conformant
implementation that replays the same DRBG through the same draw order
reproduces pk, sk, ct and ss byte-for-byte and recovers ss through decaps.

Every binding already carries this DRBG (`NistKatRng` in the AES-256-CTR-DRBG
module), so gates need no RNG of their own.

## Reproducing

`tools/ntru-plus-upstream-gen/genrun.sh` rebuilds the reference's
`PQCgenKAT_kem` for each set, refuses to proceed unless its output is
byte-identical to the shipped `.rsp`, then trims the first five records of
each file into `ntru-plus-upstream.json` and `flat/ntru-plus.tsv`
(`param_set<TAB>seed<TAB>pk<TAB>sk<TAB>ct<TAB>ss`). `RECORDS=100` vendors all
of them.
