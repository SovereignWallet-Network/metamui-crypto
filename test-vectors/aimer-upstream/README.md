# AIMer — genuine upstream KAT (conformance gate)

This directory holds the **unmodified** Known-Answer-Test records produced by
the official Samsung SDS AIMer reference implementation, **specification v3**
(KpqC final, 2026-08-26). It answers the one question nothing else in the tree
answers:

> Does our AIMer port produce and accept exactly what the *real* upstream AIMer does?

## Source (pinned for reproducibility)

- Tree: `metamui-crypto-reference/c/samsungsds-AIMer-v3/` — the authors'
  `AIMer.zip` at commit `734cc76` (2026-08-25), vendored with its `KAT/` and a
  `PROVENANCE.md`; archive SHA-256
  `4b67f9bd41005de6789bc24b86279f1c0ecf685b9de80397d8cb459bcd1bee81`.
- `tools/aimer-upstream-gen/genrun.sh` runs the vendored tree's own `make` and
  `PQCgenKAT_sign` per parameter set, refuses to vendor unless each output is
  byte-identical to the shipped `KAT/aimer-<set>/PQCsignKAT_*.rsp`, then trims
  the first `RECORDS` (default 5) records into `aimer-<set>/` and rewrites
  `SHA256SUMS`. The oracle is never a generator we wrote. The Rust port was
  verified against all 100 records per set (`RECORDS=100`) before trimming.

```
aimer-upstream/
  aimer-128f/PQCsignKAT_48.rsp   aimer-128s/PQCsignKAT_48.rsp
  aimer-192f/PQCsignKAT_72.rsp   aimer-192s/PQCsignKAT_72.rsp
  aimer-256f/PQCsignKAT_96.rsp   aimer-256s/PQCsignKAT_96.rsp
  SHA256SUMS
  v2.1/…                          (see below)
```

## Record format and how the gates replay it

Each record: `count`, `seed` (48 B), `mlen`, `msg`, `pk`, `sk`, `smlen`,
`sm = msg ‖ sig`. `PQCgenKAT_sign.c` calls `randombytes_init(seed, NULL, 256)`
(NIST AES-256-CTR-DRBG, no derivation function) and then, from that one
instance:

```
loop:                                   # crypto_sign_keypair
  pt = randombytes(λ/8)
  iv = randombytes(λ/8)
  ct = AIM3_iv(pt)   -> retry the loop on a zero S-box input
rnd = randombytes(λ/8)                  # crypto_sign_signature, RANDOMIZED_SIGNING
sig = sign(msg, ctx = "", rnd, sk)      # pre = 0x00 (ctxlen) ‖ ctx
```

Every binding's gate replays exactly that through its own `NistKatRng`, asserts
`pk`, `sk` and `sm` byte-for-byte for **all six** parameter sets, then that the
signature verifies and a flipped byte does not. A missing file fails the gate
(the oracle is tracked in this repo), and any file carrying the marker
`Generated by tools/aimer-kat-generator` is refused (anti-circularity guard from
the 2026-06 cleanup of a self-generated corpus).

## `v2.1/` — the previous specification, kept for the Rust `Aim2er*` types

Specification v3 is a new construction (AIM3 one-way function, per-S-box
multiplication checks, keygen retry): no key or signature byte is compatible
with v2.1 and the signature sizes differ. The MetaMUI node verifies AIM2-128s
signatures on a consensus path through its crypto-primitives pin, so the Rust
crate keeps the v2.1 scheme in full (`Aim2erI/IF/III/IIIF/V/VF`) beside `v3`,
and `v2.1/` holds the v2.1 records (commit `e47c497`, 5 per set) that gate it
(`tests/aimer_upstream_kat.rs`, `aimer_sign_kat.rs`, `aimer_v2_kat.rs`) and
the WASM crate (`tests/test-upstream-kat-aimer.cjs` replays keygen + sign
byte-exact for all six sets through `aimerKatFromSeed`, and verifies the `s`
sets through `WasmAIMer`). `@metamui/aimer` exposes that generation as
`AimerV21Wasm` / `createAimerV21`; its default `Aimer` / `createAimer` is v3
(#261). The other seven bindings implement v3 only. Delete `v2.1/` together
with the `Aim2er*` code once the consumer has moved its suite identifier.
